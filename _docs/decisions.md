# Decisions

Taken on 12 Oct 2026 during the spec session. Reopen only explicitly.

| Topic | Decision | Reason |
|-------|----------|--------|
| Users | Studio has accounts; client uses a guest link with a display name | Zero friction for clients; matches how studios share work |
| Room | One room = one delivery round with many images, one link | Matches real deliveries (a batch of views) |
| Pin | Point stored as % of width/height; number per image; type fix / question / like; status open / resolved (like has none) | Survives resizing; types make the export useful |
| Rounds | No versioning in v1; new render = new image, old one `superseded` | Versioning is a day of work; see _local/make-it-better #1 |
| Updates | Light polling, no WebSockets | Simpler, nothing extra to break on Render; _local/make-it-better #2 |
| Upload | Real upload from day 1, JPG/PNG ≤ 15 MB, bytes stored in the database | Render's disk is ephemeral; it is the demo |
| Extras | Client **Approve round** button and open-pin export are in v1 | Cheap and useful |
| Frontend | React + TypeScript + Vite, prototyped in Lovable, single API client in `src/lib/api/` | Course default; Lovable for a good-looking demo |
| Backend | FastAPI + uv + SQLAlchemy, modules routers / models / store / auth | Course default; reviewers expect it |
| Database | SQLite locally, Postgres in Compose and production, via `DATABASE_URL` | Rubric: supports different environments |
| Containers | One two-stage image (Node builds frontend, Python serves it) + Postgres in Compose | Course default |
| Deployment | Render (web service + managed Postgres) for attempt 1; AWS/CloudFormation considered for attempt 2 | Fastest path to a public URL |
| CI/CD | GitHub Actions: backend + frontend tests in parallel → compose stack → integration + e2e → deploy → health check | Rubric criterion 11 |
| Scope guard | Options Room and anything client-portal-shaped stays out of this repo | Private product value |
| Scope statement | The app is deliberately small: the point of the project is to exercise the full AI-native workflow (spec → contract → tests → containers → CI/CD → ops → agent extensions) end to end, not to ship a feature-complete product. The README says so explicitly. | Course rubric scores workflow discipline, not feature count |
| Comment edit/delete | Out of v1, stays in _local/make-it-better #3 even after submission | Immutable threads keep the history trustworthy |
| Env-file guard (hook rule 3) | 14 Oct 2026, owner correction from #23: an agent may create `.env` from the template with `cp .env.example .env`, and nothing else may write `.env` (no `>`, `>>`, `tee`, `sed -i`, `mv`, `cp` from a non-template). Template files and mentions of the string `.env` (grep patterns, `find -name`, loop word lists) are not secret access. | The README's first setup step was blocked for agents; a rule that blocks the documented setup gets worked around. Do not re-tighten it from `docs/` alone. |
| Agent extension layout (no symlinks) | 15 Oct 2026, recorded from issue #18 (built 14 Oct 2026): `.agents/` holds the canonical subagent and skill files; `.claude/agents/` and `.claude/skills/` are real-file copies generated by `make sync-agents`, never edited by hand; the CI job `agents-sync` (`scripts/check-agents-sync.sh`) fails when the two trees differ. There are no symlinks anywhere. | `agent-capabilities/README.md`: both trees contain real files because "this repo is developed on Windows, where symlinks are unreliable without extra privileges"; Claude Code loads only `.claude/`, while `.agents/` is the course's cross-assistant location (`docs/agent-extension-pack.md`). Issue #18 set "no symlinks (Windows dev environment)" as a constraint, and QA confirmed `find . -type l` was empty and that a deliberately introduced one-byte drift made the check fail. |
| Read-only MCP server | 15 Oct 2026, recorded from issue #19 (built 14 Oct 2026): `mcp-server/` offers exactly five tools (`health`, `list_rooms`, `room_summary`, `open_pins`, `approve_status`), each annotated `readOnlyHint=True`, and no tool that writes. The guarantee lives in the server's code and tests, not in the credential: the login it uses is an ordinary studio login, which can write through the API. See `security/agent-extension-security.md` (Risk 2); a read-only credential is proposed in the open issue #36. | `mcp-server/README.md`: the server "changes nothing in Pinpoint's backend, frontend or contract, and nothing in Pinpoint can be changed through it", it talks to the existing HTTP API only, and unit tests fail if an annotation or the read-only sentence in the server instructions is missing or if any request other than a GET (apart from the login `POST /auth/login`) is issued. `docs/agent-extension-pack.md` lists it as read-only room, pin and approval queries. The backend has no token scopes, which is why the credential cannot enforce it. |
| Hooks are guardrails, not a boundary | 15 Oct 2026, recorded from issue #22 (built 14 Oct 2026): the hooks in `agent-hooks/` (five PreToolUse rules on the Bash tool, one PostToolUse test reminder) are accident guardrails, not a security boundary. Known bypasses are documented, not closed: they match the shell string only (`bash -c`, `eval`, scripts, variables, `python -c`); the Edit, Write and PowerShell tools are not hooked; `echo $JWT_SECRET` and `printenv` are not blocked; a person or an agent that can edit `.claude/settings.local.json` can turn them off; the launcher fails open when no Python 3.8+ is found. Row 23 (env-file guard) is unchanged by this row and still decides the `.env` rule. | `docs/permissions.md` ("What the hooks cannot enforce") and `agent-hooks/README.md`: a guard that string-matches commands cannot be complete, so the docs say so instead of overclaiming. Issue #22 chose fail-open because a fail-closed launcher would block the very Bash command needed to repair a broken hook, and did not recurse into `bash -c` and `eval` strings because the issue lists them as documented gaps. The real enforcement for owner-only actions is the owner's own account permissions. |
| Security job does not gate deploy | 15 Oct 2026, recorded from issue #26: current state only. In `.github/workflows/ci.yml` the `security` job (Semgrep, `semgrep/semgrep:1.180.0`) runs on every push and pull request, and `deploy.needs` stays `[stack]`; so a red `security` job shows on the commit but does not stop a deploy. The repository owner has not decided whether it should gate the deploy; that question is open as #27 and this row does not answer it. | The comment above the job in `ci.yml` and `security/semgrep-report.md`: the registry rulesets (`p/python`, `p/typescript`, `p/secrets`, `p/owasp-top-ten`) are fetched when the job runs and are not pinned by the image tag, so a rule update or a network outage could block a deploy without any change to the code. The `agents-sync`, `mcp` and `hooks` jobs are also outside `deploy.needs`. Making a job gate `deploy` is the owner's decision (`docs/permissions.md`). |
